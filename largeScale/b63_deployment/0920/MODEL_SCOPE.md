# 预测对象、接纳下界与部署口径

本文件保留失败边界，不替代预先声明的验收标准。PDF §3.3 与 §5 明确要求：相同 CPU/Memory 预算无法覆盖的响应差异应作为模型误差和适用边界报告，不得事后增加任务类别。

2026-09-24 补充：[相同声明预算下的响应歧义分析](results/conditional-model-identifiability-20260924/RESULTS.md)按实验批次分别检查普通/分核策略。未见随机写中，c2m2/c4m2 的普通调度逐点最大误差至少为 .190893/.220307（最不稳定预算组），分核对应 .003107/.006679。该代数界仅针对已观测、声明预算相同的确定性单值预测；实际 CPU 在容差内仍不同，不能把它写成期望误差、P95 或所有环境上的不可能性定理。它支持显式建模执行条件，同时仍要求将中心预测和严格接纳分开。

## 预测与接纳是两个不同输出

原画像将单调均值网格、上角点查表和全局余量结合。上角点用于避开性能拐点的乐观插值，但它不是中心预测的最佳估计。c4m2 的独立测试直接显示：全局 MAE=.073，P95 绝对误差=.527；保守地拒绝某些实际安全点，并不能使点预测精度验收通过。

后续研究将二者显式分开：

- 中心预测 `Fcentral`：训练数据上的二维单调 L1 回归，估计条件中位数，在网格间作双线性插值。它不是条件均值，也不单独决定接纳。
- 经验接纳面 `Flower`：重复训练观测的格点最小值、二维单调下包络、上角点查询，再减去新独立校准的块最大乐观残差。求解器约束为 `Flower >= eta`，中心预测不能绕过该条件。

最小值下包络并非概率置信下界。5个校准块不足以给出所要求的有限样本95%覆盖等级，且人为设计的训练/校准分布不是可直接假设交换的样本。必须同时报告失配、保守拒绝、支持域以及实际独立部署数。

新模型使用追加训练后必须重新划分校准和测试。原最终测试已用于发现问题和设计新网格，不能再次作为新模型的“完全未见最终验证”。新拟合器不读取原测试数据。

## 固定canary本身也是资源需求

所有画像针对同一固定 canary：单任务8次1MiB SHA256，吞吐与单任务p95相对空参考取最小。它代表本文测量的VM服务能力，不是对任意应用运行时间的保证。canary会占用约一个CPU核，部署预算不能把该核凭空省掉。

现有原始训练横轴是后台注入量除以guest容量，而PDF式(16)–(17)使用包含背景的总资源压力。记训练注入量为 `z`，guest容量为 `G`，训练背景（包含固定canary预算）为 `bcal`；部署背景为 `btarget`，Pod总需求为 `d`。正确的坐标关系是：

```
training total-pressure axis = (bcal + G * z) / C
placement query             = (btarget + d) / C
raw-grid query              = (btarget + d - bcal) / G
```

`C`必须在两边相同，并按PDF取可供仿真Pod使用的有效预算，扣除明确的系统/canary保留。硬资源约束只检查`sum(d) <= C`，不会再把这些保留资源加进Pod需求。`b`用于性能压力坐标，可以包含实际背景/canary占用；此时训练轴也必须包含相应`bcal`并转换到同一个`C`。这样背景没有被重复加入硬约束。错误做法是扣减容量后原封不动使用原注入比例表，或同时在Pod需求和硬约束中再次收取相同系统保留。

CPU背景可以从无注入canary窗口的主机CPU增量减去canary实际CPU时间估计，再加固定canary预算；需保留计数噪声、调度变化和预算/实际消耗之差。内存背景可从同一无注入窗口的MemTotal−MemAvailable得到压力代理，但该代理与容器工作集不同。背景窗口必须稳定、与目标环境对应，不能将删除Pod后的回收瞬态视作稳定背景。

上述代数只解决单位和重复计量问题，不自动证明物理可迁移性。背景变化可能改变调度、页缓存和内存带宽行为，必须由K3s和真实路由负载验证。查询落在转换后支持域外时拒绝外推。

## 容器预测与节点开销

满秩路由夹具回归测的是容器CPU和工作集。真实214-Pod窗口表明，节点级CPU及内存压力增量远大于容器总量。因此单独使用容器回归会漏掉K3s、sandbox、网络和共享内核等开销。

第一轮72/71/71分布用于拟合附加每Pod项，取三节点“节点增量−容器名义预测总量”的最大每Pod残差。CPU附加项=.0007721核/Pod，内存附加项=.0088151GiB/Pod。内存项是在两种计量口径之间经验修正整体预测，不是已独立测量的物理内存分量。单窗口不能证明其随Pod数线性，36/84/94的新分布用于独立检验。

不能把三节点或214个Pod当作214次独立部署，也不能把一次零欠预算/零Q违约写成概率安全保证。仅实际完成且背景/协议/映射检查均有效的部署块计入部署证据。

## 当前坐标集成诊断的可接纳性

`buildDeploymentDiagnostic.py`由空canary窗口估计CPU背景（主机tick比例减canary实际CPU率）和不可用内存代理，显式预留canary及系统预算，再转换原画像轴。它使用现有冻结包络和原c4m2画像，只是尚未通过物理迁移的诊断实例，不得据此导出安全部署。

逐节点取最小CPU需求和最小内存需求的n个Pod（允许来自不同集合）给出乐观负载，再检查对应画像，得到容纳数量上界。放宽选择只会增加可容纳数；若所有节点上界之和仍小于214，则该经验实例不可行。η=.7/.75为195，η=.8为110，η=.85为90，η=.9/.95为87。该证明与实际硬件不可行不同：真实214-Pod已运行且测得Q>.95。

因此后续使用固定实际worker的独立低压力标定，范围CPU注入≤.12；三个worker内存注入均≤.5，使用独立15%/64MiB保护协议。域外不外推；它们是特定worker环境的画像，不冒充仅由CPU/内存规格决定且可任意迁移的F_type。

旧画像CPU轴是设定值，实际控制存在跟踪偏差；同设定点的Q差异不自动构成同实际预算的反例。旧模型坐标转换和不可行证书不能消除该混杂因素。目标worker使用累计CPU债务控制，并按预定容差检查实际跟踪；详见REVIEW_REPORT.md第4.2节。

## 首轮对照后的内存保留口径修正

首轮实例只从内存容量中另扣64MiB，采集器却要求`max(.15*guestMem,64MiB)`的可用余量。两个规则不能混称为同一可行性保证。原实例、映射、原始数据和主Q缺失记录保留。

新版`buildNodePlacement.py`从每个训练/校准/测试raw元数据读取并核对相同`memoryReserveFraction`，按`Cmem=Gmem-backgroundP95-max(fraction*Gmem,.0625GiB)`生成有效容量，节点明确记录该fraction。`refreshPlacementBackground.py`要求新实例与实际参考的fraction一致并采用相同保留；旧冻结实例缺少该字段时保留旧64MiB行为，避免改变历史复现。

新容量改变后，训练响应面轴和查询分母同时换算。7,803个相同物理需求点的Q逐项不变，旧default的refresh结果与存档完全相同；见`results/reserve-alignment-validation/summary.json`。实际需求与背景仍是估计量，所以这只是规划/采样规则一致，不能承诺绝无保护拒绝或性能违约。

修订实例`results/node-refined-reserve-aligned-placement`的内存容量为1.095635/1.014355/2.540219GiB；Pod预算、网络、η及画像Q值均不变。η=.8的乐观数量上界仍128<214，整体画像验收仍false。原network_only布局违反新增一致容量约束，必须重求可行对照，不能修改历史结果使其看似通过。
