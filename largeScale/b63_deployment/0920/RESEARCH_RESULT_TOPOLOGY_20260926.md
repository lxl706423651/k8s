# 2026-09-26：容量反例、两轮算法优化与新实例验证

本轮完成三组串行算法实验及一次只读部署容量审计。只使用主机 CPU／内存容量与拓扑；没有加入虚拟节点需求、流量画像或额外工作节点。原实验结果和失败证据未覆盖。

## 当前模型判断

容量分配定理和结构分区模型仍成立，但输入必须明确表示哪一种容量。如果给的是物理／虚拟主机标称总量，只能证明对该总量的名义预算分配可行，不能保证扣除平台开销后的实际部署或业务性能。当前测试床的 worker 是 KVM 虚拟机，不能写成在 32 台物理机器上验证过。

只给硬件总量和拓扑时，两个具有相同输入的系统可以拥有不同的操作系统／已有任务占用，因此同一正额度在一个系统可用、另一个不可用。这是信息不足的边界，无法靠调优分区算法消除。本轮没有把实测剩余资源偷偷回填为优化输入。

## 容量审计的具体反例

旧实例 N=214、分配 50/63/101，最大名义共同额度为 0.03960396 核和 0.03168317 GiB。直接将这些额度设置为每节点请求时：

|工作节点|规划总 CPU／内存 GiB|当前扣除已有 Pod 请求后的 CPU／内存 GiB|核算通过|
|---|---|---|---|
|placement-deploy0920-c2m2|1.9802 / 1.5842|1.9000 / 1.8677|否|
|placement-deploy0920-c4m2|2.4950 / 1.9960|3.8000 / 1.7989|否|
|placement-deploy0920-c4m4|4.0000 / 3.2000|3.8000 / 3.7015|否|

因此未部署已知不符合资源核算的最大额度，也没有通过缩小额度后仍声称原额度验证成功。当前 allocatable 减 Pod requests 仍不等于对所有系统开销的严格扣除。原来成功的轻载路由部署不受此反例否定；“最大额度已经部署成功”的说法则不成立。

新增 `topologyQuota.py` 对 CPU 向下取整到毫核、内存向下取整到字节。原例输出 39m、34,019,542 bytes，实际共同系数降为 0.8346，明确记录舍入损失。若 CPU 小于可表示的 1m 或映射不满足目标额度，直接拒绝。MiB 向下取整仅是容量审计中的额外敏感性检查，Kubernetes 内存并非必须按 MiB 分配。该导出只证明不超输入容量，不是在线准入证书。CPU limit 和 memory limit 也不是任意业务的服务保证。[Kubernetes 官方资源语义](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)。

## 按反馈进行的两轮优化

第一轮 `topologyRefine.py`：从 KaHyPar 输出开始，尝试单顶点以及同一 LAN 中同主机顶点组迁移，只有原容量约束满足且跨度严格下降才接受。72 个原有分区中 9 个改善、63 个不变；12 个新规模测试不变。改善集中在有容量余地的 0.8 额度条件。

第二轮 `topologySwapRefine.py`：针对最大额度下主机接近满载、单向迁移受阻，加入保持节点数不变的边界顶点交换。小边界枚举所有顶点对，大边界每主机选择最多 8 个确定性候选；每次搜索最多 2 秒，存在局部最优和候选截断。只在 2 个规模测试中得到进一步改善：4096 节点网格 687→684、692→691。其他 82 个案例不变。

此后冻结代码，再生成矩形网格和 16 成员 LAN 拓扑、512/2048 顶点、8/16 主机、种子 73/101、额度 1/0.8，共 16 个新测试。全部容量可行，7 个改善、9 个不变，完整求解约 0.05～1.34 秒。最初 12 个规模测试已参与交换规则的设计判断，因此不能作为第二轮未见验证；仅新生成这 16 个结果承担该作用。

## 与 Crescent 的关系

在先前有相同额度 Crescent 输出的 17 组中，新的快速路径按三个种子的最好值比较为 9 胜、7 平、1 负。这不同于 MILP 的 12 胜、5 平。仍然失败的是 lan64-opposed 的 0.8 额度：快速路径 S=4，Crescent 与 MILP 均为 3。优化并未消除局部最优问题。没有把不同搜索预算的最好值描述成严格等时竞争；本轮没有在更大新拓扑上重跑 Crescent。

真实 214 节点最大额度实例已由 KaHyPar 达到已证最优 S=6，当前两轮后处理未再改善，不能承诺在该例继续降低代价。全系统启动、吞吐、满载服务和统计显著性仍没有新的对比证据。

## 验证、实现选择与下一步

独立重算了前两轮 84 个分区和新验证 16 个分区的额度、主机计数和超边跨度；逐步重放第一批交换记录，核验每次下降。全部原容量约束保持。新验证还检查了整数资源数量不超输入容量，并通过不可表示额度和不合额度映射的负例。冻结代码哈希全部匹配。

当前可执行入口 `topologyPartition.py` 串联解析额度、KaHyPar、移动与交换；`topologyQuota.py` 导出保守整数数量。后处理作为质量优化选项，有收益但并非必需：追求最低求解延迟时可直接使用原 KaHyPar 后端；追求证书时仍需 MILP。不能将这些常见局部搜索算子声称为新算法突破。

下一步应优先处理两项，而非继续增加经验预测特征：①明确物理主机容量是总规格还是为仿真保留的 CPU／内存池；若坚持仅标称总量，就把部署保证留在模型结论之外。②针对保留的失败实例，研究可审计的等容量块交换或有限深度搜索，并在新拓扑上检查收益和成本；无需反复优化已知达到全局最优的真实案例。后续系统实验应随机化部署顺序并使用明确定义的资源池，测量实际建网成本，仍不要求任务画像。
