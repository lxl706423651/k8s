# 仅容量与拓扑输入：最终扩规模实验结果（2026-09-27）

本轮已完成修正后的 **214 → 3083 新分区 → 3083 Crescent 适配** 实际 VM 实验，以及固定90%预算请求的214/3083两轮完整路由验证、24 次等时间预算算法对照及独立审计。所有比较数据来自完成记录；没有把首轮失败的大规模部署计作成功。当前证据支持“公平额度分配＋拓扑分区”的定义和实现，以及本软件配置的轻载可运行性；**尚不能证明最大额度可直接兑现、未知业务QoS，或全面超过Crescent论文**。

## 1. 最终模型和实现

输入仅为拓扑超图 H=(V,E) 与承载主机 CPU/内存容量 (Ck,Mk)。不使用虚拟节点需求、CPU剖析、流量或服务时间。设 N=|V|、c0=ΣCk/N、m0=ΣMk/N，为每个顶点分配共同额度 (z c0,z m0)。

先最大化 z，要求每台主机 nk z c0≤Ck、nk z m0≤Mk；再在最大 z* 下最小化 S=Σe(|hosts(e)|−1)。固定 z 的精确可行条件为 Σk floor(min(Ck/c0,Mk/m0)/z)≥N，因此第一阶段可以精确求解，第二阶段使用异构容量约束的KaHyPar及可选改进。

共同额度是明确的公平政策输出，不是假设各程序需求相同。输入相同的两个程序实例可以有任意不同的需求，因此这些输入不足以识别任意业务的接纳或性能。完整证明、量纲和代码入口见 [模型说明](TOPOLOGY_ALLOCATION_MODEL.md)、[容量求解](topologyAllocation.py)、[快速划分](topologyPartition.py)、[候选复用](selectTopologyCandidates.py)。已有超图λ−1目标和KaHyPar本身不作为原创贡献。

## 2. 实际结果

三台worker VM：16/24/32 vCPU，32/32/64 GiB；另有8 vCPU/16 GiB管理VM，单独计费，共80 vCPU/144 GiB配置容量。这些VM共享一台物理宿主机，不能等同于跨裸金属集群验证。没有测量专用节点或Pod。

本段各规模沿用各自冻结镜像；两种3083对照逐工作负载使用相同镜像。三轮均使用固定1m CPU/8Mi requests、无limits，统一BIRD kernel export all。214与3083的BIRD版本分别为2.17.2与2.0.7，跨规模数据不作为同软件版本的性能对照。3083两种清单除nodeName外相同；模型最大共同额度**未部署**。所有稳态检查均在相同的ptp主网络与sysctl修正后运行。独立读取六份VM运行时覆盖记录，核对原始哈希及全部3083个工作负载的最终kernel配置，确认两轮逐节点完全一致；候选在运行中重配置，基线启动前配置，启动历史不同。

新分区计数为747/841/1495；Crescent适配为1027/1028/1028。本组容量的连续公平系数上界为11/12≈0.916667，整数精确最优为0.916468；这只认证第一阶段。3083的S=97尚无全局最优证书，不能把额度最优扩展为分区成本最优。对应两解的共同系数相对差异为37.38%，额外跨度下降91.70%。这两解的理论额度不同，不能写成“同最大额度门槛下胜出”。

在本VLAN+macvlan后端，一个LAN在一个参与worker上需要一个父接口。实测总数符合 A=|E|+S：3120 对 4192，总父接口数减少 **25.57%**。这是可直接核对的结构性开销；不是CPU时间、内存字节或总网卡数下降同样比例。

协议检查覆盖全部容器的配置协议数/名称、BGP Established和OSPF Full邻居数量。FIB检查为每AS固定最小r代表的BIRD网络计数与Linux路由计数关系，并非全部FIB前缀/下一跳的形式化等价证明。各试验最终UID、containerID和重启数均核对保持稳定。

拓扑探测采用每LAN固定中心的双向星形，每有向边3包、一次扫描；两组3083的探测对完全一致，共10908对。它覆盖LAN成员连通性，**不是所有端到端业务路径或负载性能**。另在214的现有容器中完成30个主网络有向对/90包及6次DNS检查，均通过，不混入上表时延样本。

本轮尚未覆盖6000秒后的下一次定期全表扫描，不能据此证明长时间稳定性。这是固定顺序、一次候选/基线配对；ICMP包不等于独立实验重复，时延差异不能称为统计显著性结论。CPU/内存只有各轮资源快照，不据此声称总体资源节省。候选和基线就绪耗时分别为1248.62/1094.59秒，包含镜像拉取且缓存历史不同，只作诊断，不能作为分区启动加速结论。

全量协议检查所观测的每容器路由网络计数，在两组3083之间有0个不一致；具体列表保留在liveSummary.json。计数相同仍不代表前缀集合等价。

## 3. 固定预留政策：从名义额度到实际调度验证

最大名义额度审计发现worker2内存请求超过Kubernetes allocatable，因此增加公开的固定预留政策ρ=0.9：每台物理容量均乘ρ，保持计数可行域和分区不变，再向下取整到毫核/字节。`topologyQuota.reserved_quantities`检查每台主机请求总额不超过90%输入容量。ρ是在上述反例之后选定的工程政策，不是测得的需求参数或通用OS开销上界。

追加试验通过required nodeAffinity指定目标worker，使用默认调度器，提交清单不含nodeName；所有请求、调度状态、映射和Pod身份均逐项检查。先用DEVICE/OSPF导出启动BIRD，再在整组load<50下每台逐个启用完整Kernel导出，之后才执行全量协议/FIB/探测。没有把调度前空闲容器检查与另一次低请求路由试验拼接成成功。逐条独立核对214/3083份Kernel启用记录，配置哈希和Reconfigured返回均一致；激活前负载采样的最大值分别为1.58/24.49。两轮与各自参考运行逐节点RIB网络计数均无差异，但这不是前缀集合等价证明。清理阶段的负载峰值完整保留在阶段图中，不混入路由验证结果。

## 4. 等时间预算验证：优化存在反例

两种策略均每次3秒，仅接受预算内完成且满足最大额度的解；超时调用全部记录但不参与选择。24次串行试验采用预登记随机顺序，3个种子；部分计时与镜像准备共享物理主机。214算法试验沿用旧容量，与本轮实际214的新VM容量不同，不混用其跨度。

|---|---|---|---|
|214|6 / 6 / 6|6 / 6 / 6|3平|
|3083|108 / 114 / 110|99 / 101 / 101|3胜|
|未见grid1536|161 / 162 / 165|164 / 166 / 166|3负|

独立程序重算24个最终解的容量断点、实际共同额度和跨度，全部一致。结论是保留直接最大额度求解作为通用路径，候选复用是可选策略；不能用单个拓扑的成功宣称普遍更优。实际部署采用此前冻结的seed307映射S=97，没有根据此次运行时延重新挑选分区。

## 5. 与Crescent的对照范围

[Crescent原文§4.3/附录B](https://www.usenix.org/system/files/nsdi24-gao-zhaoyu.pdf)的分区算法使用节点内存成本和统一容量，采用随机合并。这里因输入限制，将顶点成本设为单位成本、LAN展开为共成员边，使用其算法适配，再枚举到三台异构主机的排列。3083仅扫描预登记的3个容量×3个种子，取最高公平系数、同系数最小跨度的一解；不是穷举其全部参数，更不是完整生产系统复现。KaHyPar直接重启是另一个更强的优化器对照。

本工作的可主张内容是：一个严格受限输入下、目标与可行性定义清楚的公平资源分配问题；精确额度边界；可审计的划分实现；在固定后端下可解释并测得的接口开销，以及真实规模验证。现有数据不足以声称研究整体比Crescent更有说服力。

## 6. 失败、修复与仍未解决的边界

- 新VM的ens3起初未启用，首轮在创建namespace前停止，启用后重跑。
- systemd249的接口通配符处理在大规模接口创建时变慢；三worker应用保留参数语义的优化，每台118个参数验证一致。记录见sysctlOptimizationResults.json，依据[上游问题](https://github.com/systemd/systemd/issues/24031)。它是平台修复，不是算法贡献。
- 第一次3083在cni0恰有1023端口时持续exchange full。保留失败现场后，将主网络改为[Flannel委托](https://github.com/flannel-io/cni-plugin)的[ptp连接](https://www.cni.dev/plugins/current/main/ptp/)，重新从214开始。实验macvlan拓扑和映射没有改变。
- 大量事件导致namespace批量删除超时；完整归档事件后按UID清理；3083候选另对871个Deployment和779个Pod执行带UID前置条件的补充删除，随后自然完成namespace删除，没有强行移除finalizers。基线补充请求2123个对象；最后3083Quota90归档30393条事件，并对1653个Deployment、2660个Pod、3023个网络附件提交7336个UID删除请求，返回200或404。最终各试验完成后均清理了本轮namespace；最终四节点Ready、无残留BIRD的独立审计通过。
- 3083新分区的首次BIRD负载门禁等待1200秒仍未通过，原始失败保留。发现准备脚本使用10秒kernel扫描，与项目大规模流程的6000秒加抖动不同；运行中统一改为6000+工作负载ID哈希抖动0至120秒，保持export all。随后重新验证，基线在启动前同步应用同一配置。未重启Pod或BIRD；启动历史不同，因此只比较通过门禁后的轻载状态，不把恢复过程或启动耗时算作分区收益。详见routingRecoveryRegistration.json和kernelScan3083.json。
- 基线首次1200秒负载门槛超时；约30分钟持续高负载后尝试SIGSTOP/分批SIGCONT。该尝试未完整成功：前两台恢复完成，第三台只分批恢复324/1028个后主动终止，保护逻辑恢复了其余进程。验证器暂停期间还触发了外层1500秒编排超时，保留为编排失败，不能计作新的协议收敛失败。随后对三台临时禁用Kernel协议、保留persist配置，保持BGP/OSPF和daemon运行；每批最多每台一个实例，整组负载低于50后，逐个恢复原始Kernel配置。全部3083实例恢复后重新执行完整验证，并独立核对全部运行时配置字节及原BIRD进程启动标识。没有重启VM、Pod或BIRD；两种分区的运行历史显著不同，不能比较启动/恢复速度，轻载时延也仅作描述。原始失败、操作和恢复记录见baselinePacing/、kernelSequentialRestore/、kernelFinalStateAudit.json；Kernel persist的处理依据[BIRD 2.0.7源码](https://raw.githubusercontent.com/CZ-NIC/bird/v2.0.7/sysdep/unix/krt.c)。
- **最大额度兑现审计失败**：连续额度约0.021403核、38.963MiB；CPU向下取整至21m后，worker2的内存总请求仍超过实际allocatable，即使尚未扣系统Pod。这说明名义容量的数学解不能直接当作Kubernetes接纳证书。初始95%/90%仅为敏感性审计；其后90%政策单独登记并完成上述两轮实际验证，不能倒推最大额度也能够接纳。

## 7. 下一步优化的优先级

固定预留和取整规则已实现，并在两种规模完成requests准入及路由检查。下一优先级是在更多独立真实拓扑和未见主机比例上预登记比较，并补充3083第二阶段的下界/差距；不要用本轮测试结果训练一个自适应选策略规则再在同一数据上报收益。若要主张性能优势，再做顺序平衡、缓存条件一致的多次重复，并将负载仅作为评估条件。
