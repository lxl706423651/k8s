# E1 motivation 证据评估与补充实验要求

日期：2026-09-18

## 结论

当前结果可以支持一个较弱但真实的 motivation：

1. 通信局部性会显著影响固定 SEED 拓扑的吞吐和时延；
2. 同一台受限 VM 上的固定外生工作会随着共置数量增加而进入失约、排队和饱和区；
3. Pod 数均衡本身不能预测性能最优。

当前结果还不能支持完整的 E1 因果命题：在同一虚拟拓扑、相同容器、相同协议和相同外生工作量下，仅通过逐步改变 Pod-to-Node 映射，已经观察到“跨机通信继续减少，但共置争用使全局端到端性能反而恶化”。这个联合命题必须由 E1-B 补齐。

因此，论文目前可以把现有结果称为“两个分离的经验事实”或“E1-A 本地争用证据 + 固定拓扑局部性线索”，不能称为已经完成的 E1 trade-off/reversal 证明。

## 现有证据逐项判断

| 命题 | 当前判断 | 主要证据 |
|---|---|---|
| Pod 对象数量本身会导致明显恶化 | 不支持 | E1-A 的 75 个 Idle 点全部成功，0–200 Pod 的 P99 中位数保持约 0.450–0.522 ms |
| 固定单 Pod 工作叠加会产生本地共置代价 | 强支持 | E1-A 正式 150 点、5 blocks；Loaded 从 N=40 的 0/5 过载，经过 N=60 的 2/5，进入 N=70 的 5/5 |
| 受限 VM 存在资源饱和和运行容量边界 | 支持 | E1-A 在 N=80 首次达到约 100% CPU busy、背景完成率低于 99%；0918E1 在高并发 TCP 下出现每流吞吐下降及 140/150 运行失败 |
| 固定 SEED 拓扑中通信局部性会影响性能 | 探索性支持 | 4954/48VM 的 network-only 具有最低网络成本和最高 stress48 吞吐 |
| Pod 数方差越小性能就越好 | 现有数据反驳该简单命题 | 4954 Pod-count-balanced 的 Pod 方差最低，但 stress48 吞吐低于 optimized 和 network-only |
| 更多局部性在高共置区会被争用反超 | 尚未验证 | 现有实验没有在同一拓扑和工作量下构造单调的“通信减少/目标 VM 共置增加”映射序列 |
| 可以在部署前预测该边际取舍 | 尚未验证 | E2 旧模型仍来自未通过验收的旧 E1 数据，尚未使用 E1-A/E1-B 的配对边际样本重新拟合 |

## E1-A 提供的强证据

正式目录：[`experiments/e1_marginal_pods/20260918_e1a_formal_parallel`](./experiments/e1_marginal_pods/20260918_e1a_formal_parallel/)

实验使用相同的 4 vCPU/8 GiB worker、固定到达率、固定工作单元、无 CPU limit 的背景任务和固定 canary。15 个 N、Loaded/Idle 两组、5 个 block，共 150 点。五台 worker 只作为并行执行槽，每个 point 仍独占一台 VM；每个 worker 承担 30 点。

| N | Loaded 过载次数 | canary P99 中位数 ms | on-time 中位数 | CPU busy | run queue |
|---:|---:|---:|---:|---:|---:|
| 0 | 0/5 | 0.464 | 1.0000 | 0.006 | 1.07 |
| 40 | 0/5 | 7.343 | 0.9987 | 0.535 | 3.24 |
| 60 | 2/5 | 9.647 | 0.9923 | 0.772 | 5.37 |
| 70 | 5/5 | 17.931 | 0.9530 | 0.900 | 15.28 |
| 80 | 5/5 | 14.033 | 0.9847 | 1.000 | 80.84 |
| 140 | 5/5 | 56.265 | 0.9052 | 1.000 | 141.53 |
| 200 | 5/5 | 161.312 | 0.7708 | 1.000 | 201.97 |

该结果把本地争用的稳定正常/稳定过载区间定位为 `(40,70]`，把资源饱和起点定位到 N=80。N=140 是全范围 P99 分段拟合得到的斜率变化点，三者含义不同，不能作为统一的人为 Pod 上限。

所有 75 个 Idle 点均成功；任务计数全部守恒，cgroup CPU throttling 为 0，每点有完整 120 秒节点采样。因此 E1-A 已经排除了“仅仅创建更多 Pod”这一替代解释，并说明实际工作需求和排队才是性能下降来源。

E1-A 没有 SEED 拓扑、跨 worker 通信或映射变化，所以它只能验收本地争用机制，不能单独完成 E1。

## 0918E1 能说明什么

主要目录：[`0918E1/results/run-20260918-162011`](./0918E1/results/run-20260918-162011/)

0918E1 在十台相同的 4 vCPU/8 GiB VM 上并行运行不同规模的星型拓扑。m AS 对应 `2m+1` 个容器和 m 条 `border -> peer` TCP 流，所有容器和流都在同一 VM 内。

不限速 TCP 主批次中：

| AS/流数 | 平均每流 Mbps | 总吞吐 Gbps | RTT ms | CPU % | 内存 % |
|---:|---:|---:|---:|---:|---:|
| 60 | 2093.65 | 125.62 | 0.0332 | 97.44 | 42.42 |
| 100 | 1898.07 | 189.81 | 0.0344 | 96.31 | 63.34 |
| 120 | 1771.41 | 212.57 | 0.0407 | 97.05 | 74.80 |
| 130 | 1809.10 | 235.18 | 0.0300 | 98.30 | 78.99 |

相对 60 AS，120 AS 的平均每流吞吐下降 15.4%，平均 RTT 上升 22.3%，按预设联合门限首次越线。这个现象说明网络密集型容器集中在受限 VM 后，单流服务质量可能下降。但它不能被解释为稳定的全局反转：总吞吐在 60–130 AS 仍从 125.6 增长到 235.2 Gbps，130 AS 的 RTT 又回落到 0.030 ms。

100 Mbps/流的受控批次提供了负对照：60–140 AS 的平均每流吞吐约为 99.93–99.98 Mbps，没有检测到性能拐点。它说明相同容器数量在工作强度较低时可以正常运行，进一步支持“工作需求与争用”而非纯数量解释。

0918E1 不能直接验收 E1，原因如下：

- 每个规模改变了 AS 数、容器数和流数，并未固定同一拓扑后只改变映射；
- 所有流都在一台 VM 内，没有实际的跨机与共置映射对照；“估算减少的跨机流量”只是反事实假设，不是物理 fabric 实测；
- 不限速 TCP 的 offered load 会随系统能力反馈变化，不能充当固定外生通信量；
- 每个规模固定绑定一台 VM，三次重复是同一 VM 内的技术重复，没有跨 VM 轮换或独立 block；
- 120 AS 是首次联合越线点，RTT 不单调，尚无独立批次重复该点；
- 140 AS 是旧 75 秒命令窗口中的 Docker exec 超时，150 AS 返回 137；在 300 秒新宽限配置下尚未复跑，失败根因也未被完整区分为内存、调度停顿或 harness 超时。

因此 0918E1 适合作为“网络仿真本身也会出现单机容量压力”的辅助图，不适合作为 placement trade-off 的主图。

## 4954/48VM 对 motivation 的补充

四算法对比：[`experiments/4954_four_algorithm_comparison_20260917/detailedComparison.md`](./experiments/4954_four_algorithm_comparison_20260917/detailedComparison.md)

在相同 4954 容器、48VM 和资源规格下：

| 算法 | 网络 ratio 成本 | 跨节点网络数 | Pod 方差 | stress48 Gbps | 负载 RTT ms |
|---|---:|---:|---:|---:|---:|
| network-only | 0.256 | 1117 | 1274.957 | 232.616 | 10.721 |
| optimized | 0.593 | 3393 | 1274.957 | 170.282 | 12.126 |
| K8s default | 0.958 | 4649 | 579.415 | 153.226 | 14.145 |
| Pod-count-balanced | 0.976 | 4762 | 0.165 | 145.785 | 13.077 |

这组结果支持两点：拓扑局部性确实有性能价值；形式上的 Pod 数均衡不保证吞吐更好。network-only 与 optimized 的 Pod 数分布统计相同而网络成本不同，network-only 在本轮具有更高吞吐，也提供了局部性收益的直接线索。

它仍不能证明反转：四种算法不是沿同一批次逐步移动 Pod 的连续映射路径；每个算法只有一次完整集群运行，前三种与 network-only 分两天执行；stress 的三轮使用不同方向集合，是对应的技术窗口而非三个独立部署；现有测量还存在不可达方向和 loaded RTT 窗口限制。在该负载范围内，最强局部性方案反而是性能最好者，没有观察到争用压倒局部性收益。

## 完整 E1 还需要的最小实验：E1-B

### 固定对象

- 固定 topology 214、全部 214 个仿真 Pod、镜像、协议、路由和业务对；
- 使用 4 个相同的 4 vCPU/8 GiB worker，控制面不承载实验 Pod；
- 所有映射中全部容器同时在线，不迁移 Pod，不改变 CNI、内核或转发后端；
- 每个仿真 Pod 执行相同的固定到达工作。主档可使用 E1-A 标定的约 50m 外生需求，并预先冻结一个较低需求对照档；不得按结果逐点调负载。

### 映射序列

以约 54 Pod/worker 的可行映射为中间点，预先构造目标 worker 数量约为 `44, 54, 64, 74, 84` 的完整映射。实际点以真实准入和能够严格减少通信需求为准；E1-A 的 40–80 只用于选择扫描范围，不作为硬限制。

每一步只根据拓扑和冻结业务矩阵选择要移动的 10 个 Pod，并要求：

```text
X(pi[k+1]) < X(pi[k])
```

其中 X 是固定 offered flow 沿真实逻辑路径产生的跨 worker payload-byte crossings/s。每个映射保存完整 Pod 名单、源/目标 worker、逐节点 Pod/CPU/内存/VLAN、逻辑路径和 X。

至少增加一组“相同逐节点 Pod 数、不同跨 worker 通信需求”的配对映射，用于把局部性收益与纯 Pod 数效应分开。条件允许时再增加“通信需求接近、目标 worker 数不同”的配对映射，用于单独识别争用成本。

### 两个分开的网络子实验

1. 固定速率 UDP：所有映射使用完全相同的 offered rate、方向和持续时间；记录发送达成率、接收交付率、loss、RTT，以及单侧口径的实际 fabric bytes/PPS。用于验证静态 X 的减少确实变成跨 worker 承载量减少。
2. TCP capacity：使用同一组经过真实路由预检的固定有向流，测总 goodput、逐流吞吐、RTT、失败率和公平性。TCP 实际发送量是容量结果，不能作为固定输入或“节省流量”的证据。

旧的随机 `cross_as_multihop` 接口对不能继续使用。每个地址、方向和真实逐跳路径必须在低负载预检通过后冻结；正式高负载中的失败保留为结果，不更换样本。

### 本地和全局指标

- 目标 worker 固定 canary：P99、on-time、未完成、drop 和 pending；
- 每个 worker：CPU busy、run queue、CPU PSI、steal、softirq、内存、OOM 和 cgroup throttling；
- 局部性：静态 X、实际跨 worker bytes/PPS、UDP delivery；
- 全局性能：TCP 总 goodput、逐流分布、RTT、失败率和公平性；
- 协议正确性：全部 Pod Ready、BGP 会话、FIB、固定业务路径和真实逐跳转发。

### 重复与判定

- pilot 只用于验证准入、映射梯度和负载档位，不进入正式统计；
- 正式至少 5 个 block，block 内随机化或平衡映射顺序；每个映射重新建立干净 workload 状态；
- 以 block 内配对差值报告区间，不把同一部署内三次 iperf 窗口当成三次独立实验；
- 预先报告每一步的 `B_k = X(pi[k]) - X(pi[k+1])`、本地 `C_local` 和全局 `Delta Q`。

完整 motivation 的关键观测应为：低共置区中 `B_k > 0` 且全局性能改善或不受损；进入 E1-A 指示的高争用区后，`B_k` 仍大于 0、实际 fabric 用量也下降，但 canary/排队明显恶化，并出现 `Delta Q < 0`、全局 RTT/交付率恶化或执行停顿。如果没有出现这一反转，应如实报告“给定范围未观察到”，不能修改映射、数据或基线来制造结果。

## 是否需要重跑 0918E1

完成 E1 的最短路径是直接执行 E1-B；0918E1 不需要先重跑，因为 E1-A 已提供更干净的本地争用证据。

如果准备把 0918E1 的 120 AS 曲线作为论文主证据，则应额外复跑 100、110、120、130、140 AS：使用当前 300 秒命令宽限，至少 5 个 block，轮换“规模到 VM”的对应关系，分开固定 offered-rate 与不限速 TCP，并采集 OOM/cgroup/任务完成证据。即使完成这些，它仍是单机规模实验，只能加强本地容量证据，不能替代 E1-B。
