# E1 动机实验修订方案：固定单 Pod 工作量，刻画批量共置的边际性能代价

状态：**设计稿，尚未执行；本文不包含新增实验结果。**  
日期：2026-09-18  
适用环境：SEED Emulator / Kubernetes / libvirt VM  
替代对象：原“两个固定映射 × 每 Pod CPU 负载扫描”的 E1 设计。

## 0. 核心修改与执行优先级

本次将主要自变量从“每个 Pod 的负载强度”改为“某台 VM 同时承载的工作 Pod 数量”。每个工作 Pod 持续运行相同、固定工作量的程序，不能根据当前 CPU 利用率自动调整负载。

需要区分两个实验：

| 实验 | E1-A：单 VM 性能画像，先做 | E1-B：真实拓扑批量共置验证，随后做 |
|---|---|---|
| 是否构造 SEED 仿真拓扑 | 否 | 是，保留 topology 214 |
| VM 配置 | 固定 4 vCPU、8 GiB | 原 4 个 Worker，各 4 vCPU、8 GiB |
| 集群内工作 Pod 总数 | 随测试点变化 | 始终为同一组 214 个仿真 Pod |
| 主要改变 | 单 VM 工作 Pod 数 N | 目标 Worker 承载的 Pod 数及完整映射 |
| 每 Pod 工作量 | 固定 | 固定，且同一 Pod 在所有映射下相同 |
| 主要回答 | 再增加 10/20 个 Pod，会使固定前景任务慢多少？ | 少了多少跨 VM 通信需求，同时本地与全局性能改变多少？ |
| 可以支持的结论 | 给定配置、工作负载下的争用与边际代价曲线 | 通信局部性收益是否被共置代价抵消 |

**优先交付 E1-A。不要让 topology 214 的路由、pair plan 或 CNI 链路问题阻塞 E1-A。**

E1-A 不是 E1-B 的替代证明：没有通信映射变化，就不能声称已验证“减少通信反而更慢”。E1 也不负责证明优于 Crescent；基线比较继续留在 E3。

“临界点”属于 VM 和给定工作负载的整体状态，不属于每个 Pod。先扫描完整范围发现拐点，再在独立正式运行中测量拐点附近的批量增量，不能只挑出现恶化的两个点。

## 1. 原 pilot 的处理

原随机跨 AS 接口选择、非单调的 locality-only 映射，以及复合 penalty 的问题继续记录。旧数据全部保留在 pilot 目录，不与新设计正式数据混合。

用户提供的 51.4/33.6 Gbps 与 27.3/31.1 Gbps 仅作为值得验证的线索；本方案不把它们当作已确认结果。新 E1 不再要求复现这些数值。

## 2. 公共环境、隔离与准入

### 2.1 固定条件

- 控制平面仍使用独立的 2 vCPU、8 GiB master，不承载压力 Pod 或发包器。
- E1-A 只使用一个专用测试 Worker；其他 Worker 不运行变化中的压力任务。
- E1-B 使用原四个同构 Worker。保持 macvlan/VLAN、内核、容器运行时、真实逐跳转发与原拓扑实现不变。
- 使用实验专属 VM、网络、registry、命名空间与目录；只清理实验清单明确拥有的资源。不修改其他实验。
- 记录 K8S、内核、容器运行时、iperf3、镜像 digest、代码 commit、cgroup 版本及 VM XML/配置摘要。
- 记录 Worker→VM→物理宿主机→vCPU/pCPU 的映射。VM 间通信不自动等于物理机间通信。
- 物理机有条件时，将实验 VM vCPU 固定到不重叠的 pCPU 集合，另留控制面、测量及宿主机资源。不得未经授权调整其他 VM。无法隔离时记录同宿主机负载、CPU steal 及 vCPU 超分配情况，限定结论范围。
- 所有镜像预置。测量窗口内不拉镜像，不运行部署脚本，不批量执行 kubectl exec。

### 2.2 Pod 放置与资源策略

使用预先生成的 nodeName 实现确定性放置。nodeName 绕过调度器，但不绕过 kubelet 的实际准入与资源限制。

读取真实 allocatable.pods，并扣除系统 Pod、固定测量 Pod 和其他已存在 Pod；同时检查 CPU/内存请求准入、命名空间配额、IPAM、PID、磁盘，以及 E1-B 的实际 VLAN/接口容量。

不添加统一的虚构 Pod 上限，也不为了得到曲线私自修改 kubelet maxPods、CNI、VM 配置或集群策略。测不到足够 N 时，记录“准入截断”，在 pilot 中明确决定是否调整单 Pod 工作量后重新冻结。

为测试实际 CPU 争用，优先在隔离实验环境使用固定的 CPU requests、不设置会成为瓶颈的 CPU limits。若需要请求小于实际需求的 CPU 超分配，要在配置中明确声明并获得实验环境允许；不得把实际工作量伪装为 request。所有比较点的请求、CPU shares/weight、QoS、nice 值保持一致。

同时检查容器、Pod、QoS 和 VM/父 cgroup 的配额。如果环境必须限额，则记录 cpu.stat 与实际 quota，将配额限流和 CPU 排队分开分析。

内存先作为安全边界：负载程序使用固定小内存，不分配递增大数组，不触发 OOM 或 swap 来制造 CPU 曲线。不得使用 fork bomb、无上限线程、无限日志或无人看守的无限执行。

## 3. 长期负载程序：持续产生固定工作，不闭环追逐 CPU 百分比

### 3.1 主负载

实现一个轻量原生 CPU 任务程序；Python/shell 可以负责控制，不以频繁 fork 或 shell 死循环充当正式工作量。建议每个压力 Pod 使用一个工作进程，周期性完成固定数量的整数/哈希运算，校验结果，避免被编译器优化掉。

在空载参考 VM 上用进程/线程 CPU 时间标定每项任务的运算次数 K，然后冻结 K。

默认 pilot 起点：

- 任务到达率 λ = 10 jobs/s；
- 每任务约需参考机器 5 ms CPU 时间；
- 标称外生需求 p = λ × 5 ms = 0.05 core = 50m。

50m 是参考标定的需求标签，**不是 limits.cpu: 50m，也不是要求运行时 CPU 利用率固定为 5%**。任务数和运算次数一旦冻结，在正式扫描中不变。若 pilot 显示准入范围完全覆盖不了拐点，可事先改成另一需求等级；必须记录原因，并重新冻结所有正式点，禁止逐点调参。

### 3.2 定时与过载语义

任务 j 的计划到达时刻为：

    arrival_j = epoch + phase(pod_id, seed) + j / λ

使用单调时钟与绝对时间表。Pod 被抢占、上一任务变慢时，下一任务的计划到达时间不随之向后推迟。不能使用“计算完成后 sleep 固定时间”的闭环程序，否则过载时请求会自动变少。

为每个 Pod 设置由固定 seed 与 Pod ID 决定的相位，避免所有 Pod 每 100 ms 同时醒来。相同 Pod 在不同映射中保持相同工作序列。

维护有界队列和明确的丢弃策略，例如最多积压 5 秒对应的任务；超过上限的计划任务计入 dropped，而不是消失。程序没得到 CPU 时，也应依据理论时间表补记本应到达的任务数。禁止无限内存积压或不断创建新线程。

记录 planned_arrivals、started、completed、completed_on_time、dropped、pending_at_end、queue_age、CPU time，以及计划到达到完成的时间。结束时未完成任务不能从分母中剔除。

实现建议接口如下，**这是待 Codex 实现的接口，不是假定系统已有此命令**：

```text
pod-workload --jobs-per-second 10 \
             --work-units <pilot_calibrated_K> \
             --workers 1 \
             --phase-seed <seed> \
             --pod-id <stable_id> \
             --max-backlog-seconds 5 \
             --duration-seconds <bounded_duration> \
             --output <result_file>
```

必须支持 SIGTERM、运行截止时间、低开销本地记录、最终计数核对与清理。部署后由一次性启动参数/控制通道启动，测量中不靠逐 Pod kubectl exec 维持负载。

### 3.3 为什么不直接每 Pod 一个满核循环

满核循环作为极端 sanity check 可以存在，但它使 4 vCPU 很快进入争用区，难以观察以 10/20 Pod 为批量的转折。因此不作为主实验。ping 适合观测而不是规定 CPU 工作量；无限速 TCP 适合测最大 goodput，但不适合定义固定外生通信量。

## 4. E1-A：无仿真拓扑的单 VM 数量扫描

### 4.1 配置与自变量

只创建普通实验 Pod，不启动 BGP、不创建 AS/IXP/SEED 仿真链路。可以使用当前已有管理 CNI，不修改其后端；此阶段只宣称宿主机共置争用，不宣称测到了 SEED fabric 代价。

测试 VM 固定 4 vCPU、8 GiB。N 表示额外的工作 Pod 数，不包含始终存在的 canary 测量 Pod 与系统 Pod；输出同时给出两种数量口径。

粗扫描：

    N = 0, 10, 20, 30, ...，直到真实准入与实验安全范围允许的最大点。

N=0 是保留 canary 与系统进程的基线，不是空机器。也可预先选择 20 为粗步长，但正式主结果尽量使用 10。pilot 识别到候选转折区后，事先加入相邻的 5-Pod 细扫描点，冻结新正式点集；不能在正式结果出来后只补对假设有利的点。

每增加 10 个 p=50m 的 Pod，外生计算需求约增加 0.5 core。4/0.05=80 仅是忽略系统和前景任务开销的算术参考，不是预计拐点，更不是 admission 保证。

### 4.2 固定前景 canary

固定一个 canary Pod 在被测 VM 上，每次执行相同小任务、相同到达率和线程数。canary 与背景 Pod 共享被测 CPU，不给它独占核心，不改变它的资源权重或优先级；否则测不到背景 Pod 对已有工作的损害。

推荐主 canary 为本地计算/调度探针：周期性计划固定运算任务，记录“计划到达→实际开始→实际完成”。无需网络即可输出调度延迟和任务完成时延。

一个可供 pilot 标定的起点是 100 jobs/s、每任务 0.2 ms 参考 CPU 时间（约 20m）。正式参数与 deadline 由 pilot 冻结，不能随 N 变化。调度迟到和任务未完成均必须入账。

可额外加网络 canary：从 VM 外部稳定的测量端向该 VM 上固定服务发 UDP echo；被测服务在争用 VM 内，发包器在争用 VM 外，不放在 2 vCPU master 上。无可隔离测量端时先完成本地计算探针，不强行引入发送端瓶颈。

### 4.3 必做对照

主组 Loaded(N)：N 个 Pod 全部运行固定 p 的工作程序。

对照 Idle(N)：相同 N、相同镜像/资源设置的 Pod，只保持存活并不执行压力工作。这样可区分“Pod 存在的管理开销”和“这些 Pod 承载的工作需求”。

低成本增强：在低、拐点附近、高三个 N 上增加固定总需求组。令单 Pod 需求为 D_fixed/N，通过降低计划任务率实现，使总计算工作量近似相同；明确标注它是独立对照，不混入主扫描。这个对照也包含任务分散/唤醒开销，不能把差异全部归因于 kubelet。

建议再以 p/2 做一组数量扫描或少量预先选定点，用于说明 N 的转折随单 Pod 工作量变化。若不做，应将结论严格限定为当前 p。

### 4.4 测量协议

1. 配置该点的 N 个 Pod，确认准入、PID、内存与 canary 正常，镜像已在本地。
2. 等 Pod 创建、CNI 和启动阶段完成；创建开销另记，不混入稳态指标。
3. 使用固定 epoch 启动全部压力程序，预热 30 秒，测量 120 秒。以上是设计默认值，pilot 可统一修改并冻结。
4. 不要求超载时队列必须收敛；有界队列仍可能持续丢任务，应报告为过载结果。不能因为不稳定而无限等待或自动减载。
5. 停止压力程序、导出数据、核对任务计数并清理该点状态。下个正式点从同样的干净状态和计时条件开始。

探索可做升序扫描；正式测量在每个重复 block 内使用预先固定随机顺序或平衡顺序，重置任务队列，避免只升序导致残余积压和时间漂移。

### 4.5 主指标与边际代价

设 L99(N) 为固定 canary 的完成时延 P99；每个请求的起点是计划到达时间，而不是进程终于获得 CPU 的时间。

    ΔL_b(N) = L99(N+b) - L99(N)
    relative_slowdown_b(N) = L99(N+b) / L99(N) - 1

b 默认 10，也可用相距 20 的实测点计算 ΔL_20。跨越不同步长的点需要标明实际 b，不能混用。

同时记录：

    on_time_rate(N) = 按时完成的任务数 / 理论计划到达任务数

P99 默认是已完成样本的条件分位数。发生未完成、超时或丢弃时，必须并排显示失败率；不能因最慢任务未完成而报告“时延改善”。若失效量使总体 P99 不可识别，标注为删失/下界，不虚构单一总体 P99。

辅助指标：每 Pod/总任务完成率、积压斜率、CPU busy、run queue、CPU PSI some、steal、context switches、softirq、memory、OOM、CPU quota/throttling。CPU 利用率达到平台后仍需观测排队与任务时延，不能只画 CPU 曲线。

### 4.6 争用判据和曲线范围

E1-A 要检验的不是“有一个永远正确的 Pod 上限”，而是同一工作负载下高占用区的 ΔL_b 是否明显高于低占用区。

正式图保留所有有效扫描点、原始重复值和区间。可以事先采用“相对 N=0 的 L99 恶化 20%”作为工程参考线，但必须标注这是预设容忍度，不是硬件定律，也不能把它等同于统计意义上的唯一拐点。

若需要离线报告拐点，可在分析阶段拟合分段线性曲线并给区间，同时比较单一直线；拟合不好或没有可辨识转折时应报告“无明确拐点”。这仅为 E1 曲线摘要，不是 E2 已完成的预测模型。

## 5. E1-B：固定 214 Pod，按批增加目标 VM 的共置数量

### 5.1 不增加全网工作量

保留 topology 214 的全部仿真 Pod、镜像、网络、角色、路由配置和业务。所有仿真 Pod 均持续执行相同的已冻结工作程序。CPU 主需求等级事先固定，另可设置一组预先规定的低需求对照；不在每个映射上调整强度来追求相同 CPU 利用率。

选一个目标 Worker h，从其他 Worker 将 b=10（或事先选择 20）个 Pod 在部署计划中改放到 h，生成一串完整映射：

    π0 → π1 → π2 → ... → πK

**箭头仅表示离线方案之间的关系；每个方案在独立部署后测量，不进行在线迁移。** 每次测量中全部 214 个仿真 Pod 同时在线。切换部署所需重建时间不计入稳态性能。

例如，目标 Worker 的数量可以由约 54 逐步变为 64、74、84……，其余 Worker 的数量相应减少；实际值取决于初始可行映射和真实准入，绝不能强行要求 100+ Pod。

### 5.2 映射序列的生成

不再把 staticContentionWeight=0.1 当作 Local 标签，更不只比较两个未知质量的端点。使用容量可行的初始映射，在每一步选择一个净减少跨 VM 通信需求的批次。

选组只依据已知拓扑、固定业务矩阵和资源可行性，不能查看正式时延或吞吐后决定移动谁。优先选择与目标 Worker 内节点通信紧密的 Pod。一个批次可以来自多个源 Worker，但必须记录完整成员及源节点。

冻结每个 πk、选组 seed、group membership、每节点 Pod 数、计算需求、内存需求、VLAN/接口数与通信需求。

若不存在满足准入且减少通信需求的批次，记录“该路径的局部性梯度已耗尽”，停止此路径；不能制造虚构链路、修改业务流量或挑选实测性能最差的 Pod 来形成期望结论。需要其他起点/路径时，在 pilot 中预先固定，并把所有正式路径报告出来。

### 5.3 通信量的正确口径

对冻结业务流集合 F，每条流 f 有相同的 offered rate λ_f（payload bytes/s）和预检确认的逻辑路径 P_f。令 k_f(π) 为该逻辑路径经过的跨 Worker 转交次数。

    X(π) = Σ_f λ_f × k_f(π)
    B_k = X(π_k) - X(π_{k+1})

X 的单位是 payload-byte crossings/s，即按跨界次数加权的需求，不是端到端 goodput，不是所有网卡 RX+TX 的简单和，也不包含自动推定的封装与广播开销。

B_k > 0 表示同一 offered traffic 的跨 Worker 承载需求减少了。不能只比较业务端点是否共置；经过多个虚拟路由器的业务必须按逻辑路径统计。

共享 VLAN/IX 的广播、复制和额外封装要按照后端实际实现另计并通过计数器核验，不能将所有多端点网络机械展开成等权完全图。若只能得到逻辑代理，明确名称和边界，不伪称实测物理字节。

同时测实际 fabric bytes/PPS、每个发送端 actual/offered rate、接收交付率。优先使用固定发送速率的 UDP 独立子实验验证通信量，确保发包器确实完成相同输入；以 sender egress 计数或明确的单侧计数方式避免 TX/RX 重复。

**特别禁止：将 TCP 因过载发得更少造成的 fabric bytes 下降，解释为放置节省了通信。** 高负载下无法送足任务量的点，仍保留其真实性能结果，但通信节省分为“静态预期需求下降”与“实际实现值”，不能混称。

### 5.4 本地代价与全网代价分开测量

在目标 Worker 保留一个固定资源 canary，其他 Worker 可各保留同样 canary；它们的位置与工作量不随 πk 改变。额外测量 Pod 不计入 214 仿真 Pod，但要计入准入与资源账本。也可用既有固定角色容器承载探针，需保证方案一致。

    C_local(k) = L99_h(π_{k+1}) - L99_h(π_k)
    ΔQ(k) = Q(π_{k+1}) - Q(π_k)

Q 是固定 TCP 流计划的聚合接收端 goodput。还要报告各 Worker、各流、RTT、失败率及公平性。

C_local 描述目标 VM 上已有工作的边际损害；ΔQ 是整个部署变更后的净网络效果。源 Worker 的减压收益也属于全局变化，不能只看目标 Worker 就断言全网更差。

B_k 的单位和时延/goodput 不同。E1 以并排曲线、散点和批次表展示它们，不直接用 Gbps 减毫秒构造复合 penalty。E1-B 的 ΔQ 同时包含网络与争用的交互效应，不应被称为纯 CPU 争用代价。

### 5.5 修正原 pair plan

保留已验证的 intra_as_link 和 ebgp_ix_peer，不使用随机跨 AS 接口地址。每个映射的低负载预检要验证选定源 IP、目的 IP、方向、路由和真实仿真路径，而不是只检查 Pod 管理 IP。

原“每类 12 对”形成 24 个候选，而“16 条并发流”没有对应关系。修正为：先验证并冻结每类 12 对的候选池，再用固定 seed 每类选 8 对，得到 16 个固定有向业务对；每对恰好一个 TCP stream。另一方向可作为独立测试，不能不加说明地算成相同的 16 条流。

记录 IP、接口、逻辑路径、server port、client、并发窗口与映射关系。预检失败属于配置/准入失败；正式高负载才出现的超时、路由停顿、连接失败属于实验结果，不更换该流。

iperf3 同版本，显式设置方向、时间、连接超时、stream 数及速率；固定速率子实验用 -P 1。每个并发测试需要独立且不冲突的 server/端口，避免 server busy 被误记为网络故障。

### 5.6 两个网络测量子实验

子实验 B-traffic：固定 offered UDP 业务，记录吞吐达成率、loss、fabric bytes/PPS、固定低速 RTT 探针。主要验证通信需求减少是否真实实现，不让发包器限制造成伪节省。

子实验 B-capacity：同一组 16 个 TCP stream 并发，测接收端总 goodput。每次建议有明确预热段和至少 60 秒统计窗口，重复三次作为同一部署内技术重复；持续背景计算在测量中保持不变。TCP 的 actual sending rate 会随路径和资源改变，这是容量结果，不是固定输入实验。

两个子实验分开运行，不把它们的字节计数或不同业务强度下的 RTT 混在一个主指标里。每次子实验从相同工作量、队列起始规则和预热协议开始。

发包器尽量位于争用域之外，且不使用 master。无法外置时冻结其放置、观测其 CPU 和实际发包率，并明确结果可能包含发送/接收端争用，不伪称仅测到中间路由器转发性能。

### 5.7 E1-B 的判定

全局反转不是强制成功条件。分开报告三层证据：

1. 本地争用证据：共置增加时 C_local 变大，并伴随任务等待/PSI/运行队列证据，而非仅 Pod 数增加。
2. 局部性梯度证据：同一 offered plan 下 X 减少，健康发送点的实测 fabric 消耗也有对应变化。
3. 净效果证据：某些批次即使 B_k > 0，却出现 ΔQ < 0 或预先定义的全局时延/交付率恶化。

若低共置区有净收益而高共置区出现净损失，可报告“观察到局部性—争用权衡随占用变化”。若仅有目标 VM canary 变慢但 Q 未变差，只支持本地代价，不支持全网被反超。若没反转，保留结论与测量范围。

## 6. 重复、预注册与统计

- pilot 用于校准每任务计算量、选择能覆盖低负载/争用区的合法 N 和映射范围，不能与正式数据混用。
- 正式开始前冻结代码、镜像、workload、N 集合、映射序列、pair plan、时长、deadline、失效分类、顺序和统计口径。
- 默认五个独立重复 block。每个 block 重新建立实验 workload/部署状态，并包含所有对应比较点；block 内随机化或平衡顺序，使相邻 N/π 可以配对分析。
- 每个点内部三次 iperf 窗口是技术重复，不算三次独立部署。先在部署内聚合，再在 block 层计算均值、离散度和配对差值。
- 展示原始 block 点和 95% 区间；采用 block 层配对重采样或预先规定的配对方法。小样本区间本身不稳，不能仅靠五次运行声称极高置信度；关键现象若噪声较大需增加事先规则允许的重复并完整报告。
- 两条吞吐曲线的区间是否重叠不是配对差值的直接检验，必须计算 ΔQ 或 ΔL 的 block 内差值。
- 多批次图按探索性结果报告。需要正式显著性结论时，预先指定主比较/校正多重比较，不能事后挑最好看的相邻批次。
- 若资源只允许三个 block，则标记探索性证据，不能把它包装成已经充分验证的机制。

## 7. 故障分类、安全退出与日志

每个点保存 run_status，至少区分：

- success：工作量与采集完整，包含合法的性能恶化；
- workload_overload：任务积压、deadline miss 或网络丢包，是结果，不剔除；
- admission_failed：请求、Pod slots、CNI/IPAM/VLAN 等准入失败；
- harness_invalid：源地址/路由配置错误、server busy、采集器丢失等；
- infrastructure_failure：物理机无关任务干扰、VM 异常等，记录依据；
- safety_stopped：超出预先冻结的内存、磁盘、管理通道等安全条件。

CPU 满载本身不触发安全停止，因为它可能就是要观测的状态；OOM 风险、非实验服务受影响、磁盘耗尽等应触发停止。预设 bounded runtime 与外部清理 watchdog，不把清理成功依赖于已经饱和的 Pod。

高负载引起 Pod/进程退出时，保留失败点。该点不再满足“全部容器在线”，应标记可用性边界，不用替补 Pod 继续声称原条件满足。

监测默认每秒一次，优先节点侧低开销批量采集，不反复 kubectl top/exec 冲击控制平面。raw log 有界，写本地缓冲，测完再汇总；记录采集开销。

## 9. 给 Codex 的实施约束与验收

当前文档仅设计，不代表已获准在任何未确认集群上施压。获得实验资源授权后，按以下顺序实施：

1. 盘点当前仓库和环境，读取原 E1 harness；保留旧 pilot，不覆盖旧结果。
2. **先实现 E1-A** 的负载程序、canary、单 VM N 扫描、Idle 对照与结果分析；不依赖 SEED 拓扑就绪。
3. 加单元/小负载测试：计划任务计数守恒、超载不自减需求、固定相位、退出清理、N 定义、请求/limit 检查、边际差值计算和 raw→summary 一致性。
4. 做合法资源范围内的 pilot，冻结工作量、采样点和正式协议；保留完整 pilot 过程，不以期望结果为选点条件。
5. 执行 E1-A 正式 block，交付真实曲线。未发现拐点也正常通过脚本验收。
6. 再适配 topology 214，生成冻结的离线映射序列与批次，修复 24 候选/16 并发对应关系，预检真实路径。
7. 执行 E1-B，分别分析通信量、本地任务代价与全网 goodput；不把任一个单项自动当成因果结论。
8. E1 完成后才进入 E2。E1-A 的 N→时延曲线仅是给定 VM/工作画像的标定输入，不能原样套用到不同路由规模、PPS、BGP 更新强度或机器上。E2 必须纳入画像/网络开销并用独立场景验证。
9. E3 保留 Crescent-K8S、其 CPU 增强版与模型消融；本次 E1 不需要先实现这些基线。

验收分别评价工程正确性、数据完整性和研究假设。不能把“出现拐点/反转/胜过基线”当成脚本必须达成的成功条件。

## 10. 可用于论文的动机表述模板（必须按实际数据改写）

“为剥离复杂路由拓扑的影响，我们首先在固定配置的虚拟机上，以固定单 Pod 工作量逐步增加共置规模，并测量不变前景任务的响应时间。该实验用于识别共置代价是否随资源需求非线性变化，而不是将 Pod 数或资源不均衡直接等同于性能损失。随后，我们保持完整仿真拓扑和全网工作量不变，仅按批调整 Pod 的离线放置，联合测量跨节点通信需求、宿主机任务延迟及端到端 goodput，以检验额外通信局部性是否仍能补偿新增争用。由此，分区决策所需判断的不再是一个部署是否更集中，而是新增共置在当前承载状态下是否仍具有正的净性能收益。”

该段描述研究设计，不包含尚未观察到的实验发现。若只完成 E1-A，删去已完成 E1-B 的暗示，不能声称已证明网络仿真权衡。
