# Motivation：SEED Emulator 的 Kubernetes 放置需要同时考虑通信局部性与宿主机争用

## 研究问题

SEED Emulator 部署到 Kubernetes 集群时，Pod 并不是一组相互独立的容器。每个 Pod 对应仿真网络中的节点，Pod 之间存在固定的链路、路由器角色、协议关系和外生工作负载。部署前我们已经知道这些语义，但 Kubernetes 默认调度器主要依据资源请求、亲和性和准入约束选择节点，并不会自动把仿真拓扑转换成全局放置目标。

因此，放置一个 Pod 会同时改变两件事：

1. 它可能让通信双方位于同一台 worker 上，减少跨 worker 转发；
2. 它也可能把计算、路由协议处理、内核转发和网络中断集中到同一台 worker 上。

我们的核心问题是：

> 减少跨 worker 通信所获得的收益，是否会在某台 worker 的资源争用达到一定程度后被抵消，甚至导致整个仿真的服务质量下降？

这个问题说明，Pod 放置不能简单地等价为“最小化切边”，也不能等价为“让每个节点的 Pod 数量相同”。需要同时衡量通信局部性收益和共置造成的争用代价。

## E1 的实验思路

E1 分为两个层次。E1-A 先测量一台受限 VM 的本地容量，回答“共置负载什么时候开始使单机过载”；E1-B 再回到完整 SEED 拓扑，回答“一个具体的 Pod-to-Node 映射是否会把这种本地过载引入全局仿真”。

两部分实验都固定工作负载并重复测量，区别在于是否改变仿真拓扑中的 Pod 映射。E1-A 用于识别争用机制，E1-B 用于观察通信收益和争用代价在同一部署问题中的共同变化。

## E1-A：先确认单台 VM 存在共置过载拐点

E1-A 使用规格固定的 4 vCPU、8 GiB worker VM，逐步增加同一台 VM 上运行的工作 Pod 数量。工作 Pod 的到达率、工作量和 deadline 固定；同时设置 Idle 对照组，Idle 组只增加 Pod 数量而不执行同等外生工作。

结果可以直观地分成三个区域：

- **约 40 个工作 Pod 以内：** 5 次重复均未出现过载，任务基本按时完成；
- **约 60 个工作 Pod：** 5 次中有 2 次进入过载，说明系统已经进入重复间过渡区；
- **70 个及以上：** 5 次重复均出现过载，P99 延迟、CPU 等待和任务未按时完成开始明显恶化。

几个代表性结果如下：

| 工作 Pod 数 | 过载次数 | canary P99 中位数 | 背景任务按时率 | 最大 run queue |
|---:|---:|---:|---:|---:|
| 40 | 0/5 | 7.34 ms | 0.999 | 3.24 |
| 60 | 2/5 | 9.65 ms | 0.992 | 5.37 |
| 70 | 5/5 | 17.93 ms | 0.953 | 15.28 |
| 80 | 5/5 | 14.03 ms | 0.985 | 80.84 |
| 140 | 5/5 | 56.26 ms | 0.905 | 141.53 |
| 200 | 5/5 | 161.31 ms | 0.771 | 201.97 |

这里的 run queue 表示等待 CPU 的可运行任务数量；它从 3.24 增加到 201.97，说明系统从“任务能够及时得到 CPU”逐渐变成“任务大量排队等待 CPU”。所有 75 个 Idle 点都成功，说明性能下降不是由“创建了很多 Pod”这一数量因素单独造成的，而是由 Pod 中实际执行的工作负载与共置争用造成的。

E1-A 的结论是：**对于给定 VM 规格和工作画像，共置负载存在容量拐点。超过拐点后，继续增加工作 Pod 会使任务排队、延迟和失约显著增加。** 这里的 60 或 70 只是本实验工作画像下的观测区间，不是 Kubernetes 的通用 Pod 上限。

E1-A 只验证了本地争用机制，还没有涉及 SEED 拓扑中的跨 worker 通信。因此它不能单独说明哪一种全局放置更好，这正是 E1-B 要解决的问题。

## E1-B：在固定仿真中同时改变通信局部性和共置压力

E1-B 固定了同一个 214 Pod 的 SEED 拓扑、镜像、协议配置、路由语义、全部仿真容器和外生工作量，只改变静态 Pod-to-Node 映射。实验使用 4 个相同的 4 vCPU、8 GiB worker，所有仿真 Pod 同时在线，不进行在线迁移，也不改变 CNI、内核或转发后端。

映射序列逐步把更多 Pod 放到同一个目标 worker，同时让固定流的跨 worker 方向减少：

| 映射 | 目标 worker Pod 数 | 跨 worker 流方向 |
|---|---:|---:|
| `pi00-target044` | 44 | 16 |
| `pi01-target054` | 54 | 13 |
| `pi02-target064` | 64 | 10 |
| `pi03-target074` | 74 | 7 |
| `pi04-target084` | 84 | 4 |

因此，`pi00` 到 `pi04` 形成了一个清晰的局部性梯度：跨 worker 通信越来越少，但目标 worker 承担的仿真、转发和协议处理越来越集中。实验还包含目标 Pod 数相同但通信关系不同的 matched-count 对照，用来避免把“Pod 数量”本身误认为通信效果。

## 结果：网络流本身变快，但整体工作负载变差

E1-B 同时观察到两种方向相反的变化。

首先，跨 worker 通信减少带来了明确的网络收益。TCP dataplane aggregate goodput 从 `pi00` 的约 32.4 Gbps 增加到 `pi04` 的约 93.3 Gbps。这说明把通信相关 Pod 共置后，TCP 流少承担了一部分跨 worker 网络路径和转发开销。

但这种网络收益伴随着目标 worker 的严重资源争用：

- 最大 CPU PSI 从约 71.8% 上升到 97.2%。这表示任务越来越多地处于“想运行但暂时拿不到 CPU”的等待状态；
- 最大 run queue 从约 17.7 增加到 119.3，说明等待 CPU 的任务数量大幅增加；
- UDP 背景任务按时率从约 0.999 降到 0.609；
- TCP 背景任务按时率从约 0.997 降到 0.608；
- UDP 交付率从约 0.840 降到约 0.439。

换句话说，**TCP 网络通道本身变得更快，并不意味着整个仿真执行得更好。** 当目标 worker 被过度集中后，其他仿真任务、路由更新和工作负载需要排队，导致任务不能在 deadline 内完成，UDP 数据也不能及时交付。

`pi02` 到 `pi03` 最清楚地显示了这个转折：

- 目标 worker Pod 数从 64 增加到 74；
- 跨 worker 流方向只从 10 减少到 7；
- 但最大 PSI 从约 81.1% 跳到 94.7%；
- 最大 run queue 从约 42 增加到 88；
- UDP 背景按时率从约 0.995 降到 0.865；
- TCP 背景按时率从约 0.983 降到 0.683。

这表示在该区间内，少减少几条跨 worker 流带来的通信收益已经不足以抵消额外的共置争用。继续追求通信局部性，开始损害整体任务服务质量。

## E1 对研究动机的支持

E1-A 和 E1-B 共同建立了以下因果链条：

1. 单台受限 VM 存在由实际工作负载引起的共置过载拐点；
2. 全局 Pod-to-Node 映射可以把某台 worker 推向或推过这个拐点；
3. 减少跨 worker 通信可以改善 dataplane throughput；
4. 但过度集中会增加 CPU 等待、运行队列和协议/转发争用；
5. 因此，网络局部性收益和全局端到端性能不一定沿同一方向变化。

这正是我们引出 Kubernetes 分区算法的 motivation：

> **SEED Emulator 的 Kubernetes 放置是一个面向性能的全局分区问题。算法必须在通信局部性和宿主机争用之间寻找可解释的折中，而不能只最小化跨机边数、只平衡 Pod 数量，或只最小化资源利用率方差。**

我们的目标不是人为规定每个节点应容纳多少 Pod，而是利用部署前已经可获得的信息：

- SEED 拓扑、链路和路由关系；
- Pod 的节点角色和通信强度；
- 固定或可标定的外生工作负载；
- worker 的 CPU、内存、kubelet/CNI 准入能力；
- 小规模实验得到的争用和服务质量画像。

基于这些信息，分区算法应当在部署前估计一次共置决策的边际影响：它减少了多少跨 worker 通信，又增加了多少局部计算、转发和路由争用；只有当两者的净效果有利时，才保留这次共置。算法最终输出确定性的 Pod-to-Node 映射、镜像预置清单和可部署 manifest，并通过 Kubernetes 的真实准入约束检查。

后续章节将以此为基础介绍我们的 Kubernetes 分区算法和性能预测过程。实验中的具体 Pod 数阈值只用于标定当前机器和工作画像，不会被写成统一的人工上限；如果在其他拓扑或资源配置中没有出现相同的反转，也应保留该结果，而不是修改目标函数去制造预期现象。
